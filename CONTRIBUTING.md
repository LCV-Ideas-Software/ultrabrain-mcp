# Contributing

`ultrabrain-mcp` follows the LCV Ideas & Software native GitHub governance
baseline. Its workflows operate within this repository, without a central
controller.

## Branches and approval

- `main` is the only permanent branch.
- CI runs on pull requests targeting `main` and pushes to `main`.
- Public tags use the padded display format `v00.00.00`.
- `package.json` keeps normal npm SemVer.
- Prepare changes locally and present the diff and verification report to the
  operator. Obtain approval before committing, pushing or opening the
  implementation PR; admission follows the operator's instructions.
- Dependabot PRs use the organization's native auto-merge policy, including
  separate major updates, and must pass required checks without human review.

## Local Gates

Run in PowerShell before presenting a change for approval:

```powershell
npm ci --ignore-scripts --no-audit --no-fund
npm run biome
npm run format:public:check
npm test
npm pack --dry-run
```

Product tests, bundle/license verification and clean-consumer checks remain in
scope. Do not reintroduce Actions lockfiles or custom release-policy gates.

## Release Automation

Do not publish manually from a developer workstation.

1. Prepare the package version, its lockfile metadata, server metadata and
   changelog together; retain normal npm SemVer and the padded display tag.
2. After the approved PR merges, a push to `main` touching `package.json`
   starts `Publish`. Without a package-version change it publishes nothing.
3. A read-only build job creates one tarball through the normal npm packing
   lifecycle, including the product bundle and its license notices.
4. npm Trusted Publishing authorizes the npmjs job through OIDC in
   `npm-production`; the next job publishes the same tarball to GitHub Packages
   with the run's `GITHUB_TOKEN`. Neither writer checks out or builds the product.
5. GitHub CLI creates the padded tag and GitHub Release last, after both
   registry jobs succeed. There is no separate auto-tag workflow or
   administrative PAT publication gate.
6. Pages publishes `site/` independently; the official Linear Release
   integration remains separate from package publication.

For an interrupted publication, inspect the original run and the live registry,
tag and Release state first. Use the native
`gh run rerun RUN_ID --failed` when the failed jobs can safely resume. This is
best-effort recovery: a job can fail after an external write, so a rerun does not
guarantee exactly-once publication. Do not overwrite existing tags or assume a
tag alone proves success.

References: [GitHub package publishing](https://docs.github.com/en/actions/tutorials/publish-packages/publish-nodejs-packages),
[npm Trusted Publishing](https://docs.npmjs.com/trusted-publishers/) and
[GitHub job reruns](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs).
The [historical release recovery document](docs/HISTORICAL_RELEASE_RECOVERY.md)
is archived evidence, not an active procedure.

## Current Source Layout

Runtime source lives in `src/` (TypeScript). Build output lives in `dist/` —
generated by `npm run build` (`tsc` plus the MCP bundler) — and is never
committed. Runtime changes are made in `src/`, covered by the test suite and
smoke checks, and shipped through the release pipeline above. Governance changes
remain in the repository's own workflows and documentation.

## Security

Contributions are subject to the repository-local [inbound rights policy](INBOUND.md).

Never commit API keys, `.env`, bearer tokens, local MCP credentials,
or `node_modules/`.
